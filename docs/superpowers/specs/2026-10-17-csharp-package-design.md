# @goast/csharp — design

## Intent

Add a C# language package to goast, a peer of `@goast/kotlin` and `@goast/typescript`. It turns an OpenAPI spec into
.NET 10 code that compiles cleanly and talks to the wire exactly as the spec says. It contains five generators:

| Generator                      | Produces                                                             |
| ------------------------------ | -------------------------------------------------------------------- |
| `CSharpModelsGenerator`        | records / enums for schemas (analogue of `KotlinModelsGenerator`)    |
| `CSharpFastEndpointsGenerator` | one abstract FastEndpoints endpoint class per operation              |
| `CSharpMinimalApisGenerator`   | one abstract API class per tag + a `Map<Tag>Api` registration helper |
| `CSharpControllersGenerator`   | one abstract MVC controller per tag                                  |
| `CSharpHttpClientsGenerator`   | one client class + interface per tag, plus typed exceptions          |

Like the Kotlin package, it is built on its own AST (`cs` namespace), and every generator is an overridable class
(`protected` per-piece methods, `args.ts` argument types), so users can customise output by subclassing.

## Goals

- Generated code targets **.NET 10**, C# with `<Nullable>enable</Nullable>`, System.Text.Json, and compiles with
  **zero errors and zero warnings** under `TreatWarningsAsErrors`.
- **Strict mode** for every generator (the only mode for now; see below). The config shape must leave room for a later
  non-strict mode.
- The package plugs into all four test tiers (unit, output snapshots, compile, integration) with the same rigour as the
  Kotlin package.
- Package and publishing wiring identical to `@goast/kotlin` (build script, exports, README, CI publish step).

## Non-goals

- Non-strict mode (later).
- Newtonsoft.Json, .NET versions below 10, NativeAOT source-generated `JsonSerializerContext` (may come later).
- Generating a runnable host (`Program.cs`) — users own their host; the generators produce building blocks.

## Anti-goals

- Output that compiles but drifts from the wire contract (wrong parameter serialisation, wrong status codes). The
  integration tier exists to catch exactly this.
- Server output that forces users to touch framework types in their handler code: handlers only see generated
  request parameters and the generated strict result type.
- A C# AST that is a loose copy of the Kotlin AST with Kotlin-isms; it should model C# constructs.

## Package layout

Mirror `packages/kotlin` one-to-one (verified layout: `src/ast/{node.ts,_index.ts,index.ts,nodes/,references/,utils/}`,
`src/config.ts`, `src/file-builder.ts`, `src/import-collection.ts` → here `using-collection.ts`,
`src/generators/{file-generator.ts,models/,services/<family>/}`, `src/assets.ts`, `mod.ts`, `package.json`,
`tsconfig.build.json`, `README.md`). Each generator family has `args.ts`, `models.ts` (config/default/input/output/
context types), `refs.ts`, `<x>-generator.ts`, `<x>s-generator.ts`, `index.ts`, and colocated `*.test.ts`.

## C# AST

`export * as cs from './_index.ts'`; nodes extend `CsNode<TBuilder, TInjects>` → core `AstNode`. Each node is a
class/factory pair (`CsClass as Class, csClass as class`), with unit tests per node like the Kotlin ones.

Nodes needed (minimum):

- Declarations: `class`, `record` (class/struct record, positional or not), `interface`, `enum`, `enumMember`,
  `property` (get/set/init, `required`, initializer, expression body), `field`, `method` (incl. `abstract`, `async`,
  `static`, extension `this` parameter, expression body), `constructor` (incl. primary-constructor parameters),
  `parameter` (default value, attributes, `this`), `genericParameter` (with `where` constraints).
- Attributes: `attribute` with positional and named arguments; `attributeList` targets (`[property: ...]`) if needed.
- Expressions/values: `reference` (name, namespace, generic arguments, nullable `?`), `string` (regular, verbatim,
  interpolated, raw where useful), `call`, `argument` (positional/named), `lambda`, `collectionExpression` (`[a, b]`),
  `objectCreation` (`new T(...) { X = ... }`), `switchExpression`.
- Docs: XML doc comments (`<summary>`, `<param>`, `<returns>`, `<remarks>`), escaping `<`/`&`.
- `toNode` / `writeCsNode(s)` helpers, as in Kotlin.

`CSharpFileBuilder extends SourceBuilder`: emits `// <auto-generated/>`, `#nullable enable`, sorted `using`
directives (from a `UsingCollection`, skipping the file's own namespace and configured `globalUsings`), then a
**file-scoped namespace**, then the body. 4-space indentation. References register their namespace with the builder
when written (same mechanism as `KtReference.addImport`).

`cs.refs.*`: per-library reference factories — `system` (incl. `System.Collections.Generic`, `System.Threading`),
`systemTextJson` (+ `.Serialization`), `dataAnnotations`, `aspNetCore` (Http, Http.HttpResults, Mvc, Routing),
`fastEndpoints`, `extensionsDependencyInjection`, `systemNetHttp` (+ `.Json`, `.Headers`).

## Shared config (`CSharpGeneratorConfig`)

`OpenApiGeneratorConfig` plus: `rootNamespace` (default `OpenApi.Generated`), casings (type: pascal, property:
pascal, parameter: camel, method: pascal, enum member: pascal), `globalUsings: string[]` (default `[]` — assume
`ImplicitUsings` is off, so emit every using), `includeSourceInDocs`, `newLine`. Each generator adds a
`namespaceSuffix` (`.Models`, `.FastEndpoints`, `.MinimalApis`, `.Controllers`, `.Clients`) and a `dir` relative to
`outputDir`. One top-level type per file, file named after the type.

## Models generator

Config additions: `immutableTypes` (**default `true`**), `oneOfBehavior`, `emptyObjectTypeBehavior`,
`addDataAnnotations` (default `true`). Schema normalisation (discriminated bases, `allOf` inheritance, inheritable
schemas, `shouldGenerateTypeDeclaration`) follows the Kotlin model generator's logic.

- Object → `public sealed record Pet` (or non-sealed `record` when it has derived types). Properties:
  - `immutableTypes: true` → `{ get; init; }`, arrays as `IReadOnlyList<T>`, maps as `IReadOnlyDictionary<string, T>`.
  - `immutableTypes: false` → `{ get; set; }`, `List<T>`, `Dictionary<string, T>`.
  - required → `required` keyword; optional → nullable (`T?`) unless it has a default, which becomes the initializer.
  - every property has `[JsonPropertyName("wire-name")]`; nullable-but-required follows the Kotlin rules.
- Discriminated `oneOf` / `allOf` bases (Kotlin interfaces) → `public abstract record` with `[JsonPolymorphic(
  TypeDiscriminatorPropertyName = "...")]` and one `[JsonDerivedType(typeof(Sub), "value")]` per mapping; subtypes
  inherit from it.
- Enum → C# `enum` with `[JsonConverter(typeof(JsonStringEnumConverter<T>))]` and `[JsonStringEnumMemberName("wire")]`
  per member. Integer enums map to numeric enum values.
- `additionalProperties` → `[JsonExtensionData] public IDictionary<string, JsonElement>? AdditionalProperties`
  (typed `additionalProperties` schemas that aren't `true` → a dictionary-typed property where expressible).
- Formats: `date-time` → `DateTimeOffset`, `date` → `DateOnly`, `time` → `TimeOnly`, `uuid` → `Guid`, `uri` → `Uri`,
  `int64` → `long`, `int32` → `int`, `float` → `float`, `double`/number → `double`, `decimal` → `decimal`,
  `binary` → `Stream` (in bodies) / `byte[]` (base64 `byte` format), free-form → `JsonElement`.
- DataAnnotations (when enabled): `[Required]` is implied by `required`; add `[StringLength]`/`[MinLength]`/
  `[MaxLength]`, `[Range]`, `[RegularExpression]`, `[EmailAddress]` as Kotlin does for Jakarta.
- Doc comments from `title`/`description`, `[Obsolete]` for deprecated.

Output: `ctx.output.csharp.models[schemaId] = { type: cs.Reference }`, consumed by the service generators exactly like
`KotlinModelsGeneratorOutput`.

## Strict mode — server side (FastEndpoints, Minimal APIs, Controllers)

Config: `mode: 'strict'` (a single-value union today, reserved for `'lenient'` later). Optional per-endpoint override
via the same custom extension mechanism Kotlin uses for `strict-response`, if cheap — builder's call.

For every operation a **result type** is generated in the generator's namespace, e.g. `GetPetByIdResult`:

```csharp
public abstract record GetPetByIdResult
{
    private GetPetByIdResult() { }
    public static GetPetByIdResult Ok(Pet body) => new OkResponse(body);
    public static GetPetByIdResult NotFound() => new NotFoundResponse();
    public static GetPetByIdResult Default(int statusCode, Error body) => new DefaultResponse(statusCode, body);

    public sealed record OkResponse(Pet Body) : GetPetByIdResult;
    public sealed record NotFoundResponse() : GetPetByIdResult;
    public sealed record DefaultResponse(int StatusCode, Error Body) : GetPetByIdResult;
}
```

- One factory per documented response key (`200`, `404`, `2XX`, `default`). Range and `default` keys take the status
  code as a parameter. Response headers declared in the spec become factory parameters. Multiple content types per
  response: the factory takes the content type when it matters for serialisation (builder's call how).
- The result type is identical in shape across all three server generators, so moving handlers between frameworks is
  mechanical. Each generator emits its own copy in its own namespace (they can coexist).
- Handlers (user code) implement an abstract method `Task<GetPetByIdResult> GetPetByIdAsync(<params>,
  CancellationToken cancellationToken)`. Parameters are typed from the spec (path/query/header/cookie/body), named in
  camelCase, optional ones nullable.
- The generated glue converts the result to the framework's output with an exhaustive `switch` on the nested types.

Per framework:

- **Controllers** — `public abstract class PetsControllerBase : ControllerBase` per tag with `[ApiController]`,
  `[Route]`/`[HttpGet(...)]`, `[FromRoute]/[FromQuery]/[FromHeader]/[FromBody]` (with wire names), `[Produces]`/
  `[ProducesResponseType]`. Each action is non-abstract, calls the abstract `...Async` method, and returns
  `IActionResult` built from the result.
- **Minimal APIs** — `public abstract class PetsApiBase` per tag with the abstract methods, plus a static class with
  `public static RouteGroupBuilder MapPetsApi(this IEndpointRouteBuilder app)` that maps every route with typed
  binding attributes and resolves `PetsApiBase` from DI (`[FromServices]`). Routes return
  `Results<Ok<Pet>, NotFound, ...>` (falling back to `IResult` where a case cannot be expressed as a typed result, e.g.
  `default`), so OpenAPI metadata is correct.
- **FastEndpoints** — per operation `public abstract class GetPetByIdEndpointBase : Endpoint<GetPetByIdRequest,
  ...>` (or `EndpointWithoutRequest`) with a generated request DTO carrying FastEndpoints binding attributes
  (`[RouteParam]`, `[QueryParam]`, `[FromHeader]`, `[FromBody]`, `[BindFrom("wire")]`). `Configure()` is sealed and
  pre-filled (verb, route, `AllowAnonymous` is **not** set — auth is the user's concern; builder may expose a
  `protected virtual void ConfigureEndpoint()` hook). `HandleAsync` calls the abstract `ExecuteAsync(request, ct)` and
  sends the result via `Send.*`/`HttpContext.Response`.

Parameter serialisation (style/explode, arrays, deep objects) must match what the reference client in the test
harness sends; where a framework cannot bind a form natively, generate the parsing in the glue.

## Strict mode — client side (`CSharpHttpClientsGenerator`)

- Per tag: `public interface IPetsClient` and `public class PetsClient : IPetsClient` taking `HttpClient` via
  constructor. One `Task<T> GetPetByIdAsync(<params>, CancellationToken cancellationToken = default)` per operation;
  `Task` when the success response has no body. The **first success (2xx) response** defines the return type; other
  2xx responses are treated as success, like in the other generators.
- `services.AddPetsClient(Action<HttpClient>? configure = null)` extension registering it with
  `IHttpClientFactory` (`AddHttpClient<IPetsClient, PetsClient>`), returning `IHttpClientBuilder`.
- Exceptions (in the clients namespace):
  - `public class ApiException : Exception` with `StatusCode`, `ResponseHeaders`, `ResponseBody` (string). Thrown for
    **every** non-success HTTP status, documented or not.
  - Per documented error response: `public sealed class GetPetByIdNotFoundException : ApiException` with a typed
    `Body` when the response has content. `default`/range error keys get one class each (`...DefaultException`).
  - Anything that is not an HTTP error status (DNS, connection reset, timeout, cancellation) surfaces as whatever
    `HttpClient` throws (`HttpRequestException`, `TaskCanceledException`, ...). The client never wraps those.
- Request building covers path/query/header/cookie parameters with OpenAPI style/explode rules, JSON bodies,
  `application/x-www-form-urlencoded`, `multipart/form-data`, raw/binary bodies, and response bodies
  (JSON, text, binary as `Stream`/`byte[]`). Shared helpers (query encoding, JSON options) are generated once into the
  clients namespace (via AST or an asset — builder's call).
- JSON uses one shared `JsonSerializerOptions` (web defaults, `JsonStringEnumConverter`), exposed so users can
  override.

## Testing (all four tiers)

1. **Unit** — one `*.test.ts` per AST node and per generator (`model-generator.test.ts`, etc.), as in Kotlin; builder
   tests pin `newLine: '\n'`.
2. **Output snapshots** — add C# profiles to `test/output-tests/profiles.ts` (widen `Profile.language`):
   `models` (immutable), `models-mutable`, `fastendpoints`, `minimal-apis`, `controllers`, `http-clients` (each
   service profile also runs the models generator). Snapshots land in `test/output/csharp/...`.
3. **Compile** — `test/docker/csharp` image on `mcr.microsoft.com/dotnet/sdk:10.0` with a warmup project that
   restores every NuGet package used (pinned versions: FastEndpoints, plus framework refs) so builds run with
   `--no-restore`/offline against the warmed cache. `runners/csharp.ts` synthesises one project per unit (hash-named
   like Gradle subprojects) in a solution, builds with `TreatWarningsAsErrors`, parses MSBuild diagnostics
   (`path(line,col): error CSxxxx: msg`) via `test/harness/compile/parse-csharp.ts` (+ test). Add `CSharpCompileLanguage`,
   a `CSHARP_PROFILES` group, a `describe('csharp (dotnet)')`, discovery-test updates, `MINIMUM_UNITS`, and
   `test/harness/csharp/dependencies.ts` (single source of package versions, mirrored by the warmup csproj).
4. **Integration** — against the committed `test/output/csharp/<profile>/integration/kitchen-sink/` tree:
   - `test/integration/csharp-clients/`: a hand-written C# console driver calling every case through the generated
     client in table order and printing `##GOAST-CASE##{...}` lines; the test runs it in the dotnet container against
     `startRefServer`, diffs with `diffRequest`/`diffResult`, snapshots to `test/wire/<profile>/`. The driver reports
     `ApiException` subclasses as the case result so error-status cases are verified too.
   - `test/integration/csharp-servers/`: hand-written implementations for each of the three server generators (shared
     case data/expectation helpers, 599/598/597 failure convention as in `spring-controllers`), a readiness endpoint,
     run via `startContainer` and driven with `issueCase` + `diffResponse`. Plus a boot test per server unit.
   - Register targets in `test/integration/targets.ts`, filters in `task-filters.test.ts`, scripts in root
     `package.json`, jobs in `.github/workflows/build.yml` (image matrix, `compile-csharp`, `it-csharp-*`,
     `all-tests.needs`, publish loop + publish/tag steps).
   - Cases that a C# framework genuinely cannot express go into `except` entries in `test/cases/cases.ts` with a
     reason, never silently.

## Implementation deviations

- **FastEndpoints:** there is no request DTO. Endpoints derive from `EndpointWithoutRequest` and generated parsing
  (`ApiEndpointSupport`) reads everything from the `HttpRequest`, so FastEndpoints' binding and validation never run.
  The abstract handler is named `<Op>Async`, because FastEndpoints already uses `ExecuteAsync`.
- **Minimal APIs:** routes always return a generated `IResult` rather than a typed `Results<...>`, for wire fidelity.
  Metadata comes from `.Produces` and `.Accepts`.
- **Multipart files:** server handlers receive them as `IFormFile`/`IFormFileCollection`; client file parameters use the
  generated `ApiFile`.

## Decided by the user

- .NET 10; strict mode for every generator; non-strict maybe later.
- Server: abstract handler methods returning a per-endpoint strict result type translated per framework.
- Client: return first success body or `Task`; `ApiException` base for every HTTP error status (documented or not);
  a subclass per documented error; non-status failures use the standard `HttpClient` exceptions.
- Models: records, `required`, `[JsonPropertyName]`, polymorphic abstract records, enums with
  `JsonStringEnumMemberName`, `[JsonExtensionData]`, DataAnnotations option; `immutableTypes` option, default on.
- Server/client shapes as described above (controllers per tag, minimal-API class + `Map<Tag>Api`, FastEndpoints per
  endpoint, client + interface + `Add<Tag>Client`, namespaces under `OpenApi.Generated`).
- All four test tiers.

## Settled after the builder check (Claude's calls)

- **Null vs absent.** Optional properties are nullable and carry `[JsonIgnore(Condition =
  JsonIgnoreCondition.WhenWritingNull)]`, so absent stays absent. Required properties are always written; a required +
  nullable schema becomes `required T?`. Defaults become initializers and are always written.
- **Wire fidelity bar.** All three server generators and the client must pass every case in `test/cases`; framework
  binding gaps are closed with generated parsing glue. `except` entries are allowed only for genuine framework limits,
  each with a reason.
- **Response content type (server).** A response with one content type uses it. With several, the factory takes the
  content type as a parameter (defaulting to the first declared). No `Accept` negotiation.
- **Undocumented statuses (server).** The result type only allows documented responses (`default`/range keys allow
  any code in their range). Unhandled exceptions are left to the framework (500). The integration servers' 599/598/597
  convention uses an exception filter/middleware in hand-written test code, as Spring does.
- **Environment.** dotnet only ever runs in Docker, like gradle; the image warmup restores NuGet with network at image
  build time, and builds run with `--no-restore` afterwards.
- **Models fallbacks.** Where `required`/`init`/polymorphism combinations are rejected by the compiler or STJ,
  falling back (e.g. `[SetsRequiredMembers]` constructors or dropping `required`) is fine. `oneOf` without a
  discriminator follows `oneOfBehavior` exactly as Kotlin (merged properties); no custom union converters.
- **Tags.** Untagged / multi-tagged operations are grouped exactly like the Kotlin service generators (core's
  `ApiService` grouping).
- **Versions.** `mcr.microsoft.com/dotnet/sdk:10.0`; latest stable FastEndpoints supporting `net10.0`.
- **Publishing.** Mirrors `@goast/kotlin` (own version, publish/tag step in CI).
