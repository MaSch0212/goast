# CI Rework Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the single-job `build.yml` with the job graph the testing-strategy spec specifies, so every tier runs as its own CI job and publishing happens only when all of them pass.

**Architecture:** One workflow, ~15 jobs. A composite action carries the Deno setup every job repeats. `lint`, `unit` and `output-check` are the cheap gates; `images` warms the Docker layer cache once; the compile and integration jobs fan out from there; an `all-tests` aggregator collapses the fan-out into a single gate that `publish` depends on.

**Tech Stack:** GitHub Actions, Deno, Docker Buildx with `type=gha` cache.

## Global Constraints

- **Only Deno and Docker may be required as prerequisites.** Every other toolchain lives inside a container.
- **No production code under `packages/` changes** except `packages/*/deno.json` metadata where a task explicitly calls for it. A generator change would break byte-exact tier-2 snapshots.
- **No test expectations change.** No file under `test/output/`, `test/compile/`, `test/wire/` or `test/cases/` is edited by this plan. If a task makes one of them fail, that is a finding to report, not a snapshot to regenerate.
- **Tier 3 must stay at exactly 67 committed diagnostic files** under `test/compile/`.
- **`test/harness` is JSR-published**: every export needs an explicit type annotation or `deno lint` fails `no-slow-types`.
- **`deno task test` must never start a container.** Docker legs gate on `GOAST_INTEGRATION`; tier 3 gates on `GOAST_COMPILE`.
- **One Deno version.** The version the workflow pins and the version the committed snapshots were generated with must be the same, or tier 3 fails in CI for a reason that has nothing to do with the generator.
- `deno fmt --check` and `deno lint` must pass. Line width 120.
- Do not run `git checkout --` on any file in this repo — it rewrites line endings and breaks `deno fmt --check`. Use `git show HEAD:<path> > <path>`.

## What is measured, and true, right now

Established before this plan was written. Do not re-derive; do not assume anything beyond these.

1. **`deno task test:all` is green end to end** on Deno 2.9.5: unit 215/2411, tier 3 16/853 (67 files), sweep 14/63, kotlin 7/13, controllers 8/29, angular 3/9, k6 2/11, stubs 5/11.

2. **`deno task npm` is broken, and has been since tier 3 landed.** It fails with 15 dnt diagnostics, all in `src/harness/docker.ts` — `Property 'Command' does not exist on type 'typeof Deno'` (×6) and one `TS2504` on `ReadableStream` async iteration. CI has never caught this because `build.yml` only triggers on `main` and this work has lived on `testing-next`.

   The mechanism: `packages/core/deno.json` declares `"usedLocalPackages": ["@goast/test-harness"]`, which makes `scripts/build_npm.ts` copy the harness into the npm output tree, where dnt type-checks it under a Node shim that has no `Deno.Command`. `scripts/build_npm.ts:58` sets `test: false`, so dnt builds no tests at all — which is the only thing the harness was there to serve. This is precisely the question the spec's Migration section left open: *"Whether the `npm:test-utils` dnt task is still required — it exists so dnt can type-check package-internal tests — is verified during implementation and the task is dropped if not."*

3. **`deno publish --dry-run --allow-dirty` succeeds** on Deno 2.9.5.

4. **The workflow pins Deno `v2.8.2`**, twice, with a comment saying 2.8.3 regressed `export =` default-import type resolution (`import fs from 'fs-extra'`). That pin is now actively dangerous: the tier-3 host snapshots committed in `173122a` record Deno 2.9's parse-error wording (`SyntaxError: Expected '{', got '='`). On 2.8.2 the same units produce `The module's source code could not be parsed: …` and **tier 3 fails in CI**.

5. **`buildImage` already does the right thing for CI caching** (`test/harness/docker.ts:166-189`): it derives a content-hash tag, skips the build when that tag exists locally, and uses `--cache-from type=gha --cache-to type=gha,mode=max` when `CI` is set, a local cache dir otherwise. The `images` job does not need a different build path — it needs to invoke this one.

6. **There are three Dockerfiles, not four**: `test/docker/{kotlin,node,k6}/Dockerfile`. The spec's "four" predates the decision not to add a Playwright image.

7. **Filter strings for splitting existing tasks into jobs**, all `describe` names:
   - tier 3: `typescript/host (deno check)`, `typescript/<profile> (tsc)`, `kotlin (gradle)`
   - kotlin clients: `integration/okhttp3-clients@sb3`, `@sb4`, `integration/spring-reactive-web-clients@sb3`, `@sb4`
   - controllers: `integration/spring-controllers@sb3`, `@sb4`, `@sb3-strict`, `@sb4-strict`

8. **`test:compile:check` also runs `test/harness/docker.test.ts`**, which is a harness test rather than a compile unit and starts containers of its own.

### Task 3: The task entries the job split needs

**Files:**
- Modify: `deno.json`
- Test: `test/integration-tests/` — see Step 1

**Interfaces:**
- Produces these task names, used verbatim by Task 4's workflow:
  ```
  test:compile:ts:check      typescript units only  (host + tsc), GOAST_COMPILE=1 GOAST_SNAPSHOT=check
  test:compile:kotlin:check  kotlin units only,     GOAST_COMPILE=1 GOAST_SNAPSHOT=check
  test:harness:docker        test/harness/docker.test.ts on its own
  ```
  Integration jobs reuse the existing `test:integration:*:check` tasks; the two that need per-unit matrices pass a filter through, so they need no new task — Task 4 invokes `deno test` with `--filter` directly for those and the plan says so there.

**Context:** fact 7 gives the filter strings, fact 8 the reason `test:compile:check` cannot simply be split in two: it also runs `test/harness/docker.test.ts`. Splitting the compile gate without accounting for that file either runs it twice or drops it.

**The trap this task must avoid:** `deno test --filter` silently passes when it matches nothing. A task that filters to a typo runs zero tests, exits 0, and the CI job it backs is vacuously green forever. That is the same class of failure as tier 4's absent-artifact inversion, and it needs the same treatment — a test that asserts the filters match.

- [ ] **Step 1: Write the failing test**

Create `test/integration-tests/task-filters.test.ts`. It reads `deno.json`, extracts the `--filter` argument from each task that has one, and asserts each matches at least one `describe` name that actually exists.

```ts
import { expect } from '@std/expect';
import { describe, it } from '@std/testing/bdd';

import { repoRootDir } from '@goast/test-harness';

// Every `--filter` in deno.json, paired with the task that carries it.
function filtersFromTasks(tasks: Record<string, string>): { task: string; filter: string }[] {
  const found: { task: string; filter: string }[] = [];
  for (const [task, command] of Object.entries(tasks)) {
    const match = /--filter\s+(?:"([^"]*)"|'([^']*)'|(\S+))/.exec(command);
    if (match !== null) found.push({ task, filter: match[1] ?? match[2] ?? match[3] });
  }
  return found;
}

describe('deno task --filter arguments', () => {
  it('every filtered task matches at least one suite name', async () => {
    // `deno test --filter` exits 0 when it matches nothing, so a typo makes the CI job that runs the
    // task vacuously green — permanently, and with no signal. This is the only thing standing between
    // a renamed `describe` and a gate that silently stops gating.
    const denoJson = JSON.parse(await Deno.readTextFile(`${repoRootDir}/deno.json`));
    const filters = filtersFromTasks(denoJson.tasks);

    expect(filters.length, 'no filtered tasks found — has deno.json changed shape?').toBeGreaterThan(0);

    const sources = await collectSuiteNames();
    for (const { task, filter } of filters) {
      expect(sources.some((name) => name.includes(filter)), `task \`${task}\` filters on \`${filter}\`, which matches no suite`)
        .toBe(true);
    }
  });
});
```

Write `collectSuiteNames()` yourself: walk `test/` for `*.test.ts`, read each, and pull the string literal out of every `describe(` call. Template literals (`` describe(`integration/${unit.id}`) ``) cannot be resolved statically — handle them by also collecting the unit-id constants those files iterate (`DRIVER_UNITS`, `SERVER_UNITS`, the compile profiles) or, if that proves brittle, by matching on the literal prefix before the first `${`. Say in your report which approach you took and what it cannot catch.

### Task 4: The workflow

**Files:**
- Modify: `.github/workflows/build.yml`

**Context:** this is the spec's job graph, reproduced here so you do not need the spec open:

```
lint --+
unit --+
output-check --+-> compile-ts ------------+
images --------+-> compile-kotlin --------+
               +-> it-fetch-clients ------+
               +-> it-angular-services ---+
               +-> it-k6-clients ---------+-> all-tests --+
               +-> it-easy-network-stub --+               +-> publish
               +-> it-okhttp3-clients ----+               |   (main only)
               +-> it-spring-reactive-web-+               |
               +-> it-spring-controllers -+               |
build (jsr dry-run + dnt npm) ----------------------------+
```

Requirements, each with its reason:

- **`images`** — matrix over the three Dockerfiles (fact 6), building each so downstream jobs get GHA layer hits. `buildImage` already emits the right cache flags when `CI` is set (fact 5), so this job should invoke that code path rather than hand-rolling a `docker buildx build`. A one-line `deno eval` calling `buildImage` per context is enough; if you add a task for it, it needs a filter guard only if it uses `--filter`.
- **`output-check` gates compile and integration**, because both read the committed tree and validating a stale tree produces misleading results. It is a sub-minute job, so the serialization is cheap.
- **Matrix expansions** — `it-spring-reactive-web` over SB3/SB4, `it-spring-controllers` over SB3/SB4 × strict/non-strict, using the filter strings in fact 7. `it-okhttp3-clients` likewise splits from the kotlin task.
- **`all-tests`** — an aggregator with `if: always()`, failing when `contains(needs.*.result, …)` matches `failure`, `cancelled`, **or `skipped`**. Treating *skipped* as failure is deliberate: a mis-authored job-level `if` must never silently open the publish gate. `publish` then needs only `[all-tests, build]`.
- **Concurrency** — `cancel-in-progress` for pull requests only, never on `main`, so a publish run cannot be killed mid-flight.
- **Failure artifacts** — `snapshot.patch` from `output-check` (`git diff > snapshot.patch` on failure); driver stdout and container logs from failed integration jobs.
- **Triggers** — integration jobs run on every push and every pull request. A client-serialization regression should be caught before merge, which is the purpose of the tier.
- Every job uses `- uses: ./.github/actions/setup` after checkout.
- `publish` keeps its existing steps and its `if: github.ref == 'refs/heads/main'` verbatim. Do not restructure the publishing itself; this plan changes what gates it, not what it does.

**On timeouts:** the current file uses `timeout-minutes: 20` for everything. Set each job's from its measured local runtime (fact 1) plus generous headroom for a cold CI runner — the Kotlin and controllers legs take ~2 and ~3 minutes locally with a warm Gradle cache and will take considerably longer cold.

## Self-review notes

- **Spec coverage.** Every bullet of the spec's CI Workflow section maps to a requirement in Task 4, except the Dockerfile count, which fact 6 corrects.
- **The one thing this plan cannot verify.** No task can actually run the workflow. Every task that touches `.github/` says so explicitly and confines itself to checks a careful read can make. The first real run is on the first push, and it should be expected to need a fixup commit or two — that is not a failure of the plan.
- **Ordering is load-bearing.** Task 1 before Task 2 because Task 2's evidence that the Deno pin can move is Task 1's successful `deno task npm`. Task 3 before Task 4 because the workflow invokes the tasks by name.
